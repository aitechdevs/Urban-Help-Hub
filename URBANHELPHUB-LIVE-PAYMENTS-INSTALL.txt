URBANHELPHUB PAYPAL PAYMENTS — INSTALLATION

1. Deploy backend-api and web-app together. Back up the database first.
   From backend-api: composer install --no-dev --optimize-autoloader
   php artisan migrate --force
   php artisan optimize:clear
   From web-app: npm ci && npm run build
   Restart the application processes after configuration changes.

2. Configure a PayPal REST application with Orders v2 and Payouts access.
   Start with sandbox accounts. The platform merchant must be approved for
   Payouts and be able to receive the supported transaction currencies.
   Securely set backend runtime values, never in frontend code or chat:
   PAYPAL_MODE=sandbox (change to live only after sandbox acceptance)
   PAYPAL_CLIENT_ID
   PAYPAL_CLIENT_SECRET
   PAYPAL_MERCHANT_ID (platform's PayPal merchant account ID)
   PAYPAL_WEBHOOK_ID (the endpoint ID for the selected REST application)
   FRONTEND_URL=https://your-frontend-domain
   Allow HTTPS to api-m.sandbox.paypal.com and api-m.paypal.com.
   These credentials use OAuth Basic authentication and must be available
   to the backend process; encoded proxy placeholders are not raw secrets.

3. Register https://your-api-domain/api/paypal/webhook in PayPal and save
   its webhook ID. Subscribe to PAYMENT.CAPTURE.COMPLETED,
   PAYMENT.CAPTURE.REFUNDED, PAYMENT.CAPTURE.REVERSED,
   CUSTOMER.DISPUTE.CREATED, and all PAYMENT.PAYOUTS-ITEM events,
   including SUCCEEDED, FAILED, DENIED, BLOCKED, HELD, UNCLAIMED,
   RETURNED, REFUNDED and CANCELED where supported.
   The backend verifies signatures through PayPal and retrieves payout
   status from PayPal. A browser redirect alone is never proof of payment.

4. Helpers save their PayPal email in their dashboard. A helper proposes
   a fixed task quote when accepting an opportunity; the customer sees
   and accepts that quote at matching. The price then stays fixed.
   Price changes, cancellations and refunds need separate admin handling;
   no automatic quote changes or refunds are introduced in this release.

5. The customer pays 50% via PayPal when confirming the helper. Work cannot
   start before a completed capture. The helper reports completion, and
   the customer confirms satisfactory completion and pays the remaining
   balance. For odd cents, the commitment rounds to the nearest cent and
   the balance is the exact remainder. Both funds remain with the platform.
   This is a platform-managed payment hold, not a PayPal escrow product.

6. The helper receives 60% of the agreed service price, rounded in minor
   units; the platform receives the remainder (40%). Collection fees,
   payout fees and applicable taxes are platform expenses and never reduce
   helper earnings. Prices include applicable taxes. The admin must review
   and enter the actual tax liability in task currency when releasing a
   payout (enter 0 only when appropriate). Tax rates are not guessed and
   the application does not file or remit taxes automatically.
   Finance views show platform share less recorded provider fees and tax.
   CAD reporting uses the configured FX snapshot; replace indicative FX
   values before live use. Unsupported PayPal currencies are rejected,
   rather than silently converted. A configured CAD reporting rate is
   also required for each supported transaction currency.

7. Admin confirms with the customer that work is complete, reviews the tax,
   and releases the entire helper payout. Both verified captures and the
   customer's stored completion confirmation are required. PayPal Payouts
   is asynchronous: submitting a batch does not mark earnings paid. Use
   Refresh PayPal payout status or await a verified webhook for SUCCESS.
   Failed, blocked, returned, denied or unclaimed transfers require review.

8. Payout submission intent is saved before the provider call. An uncertain
   network result remains processing and cannot be submitted again. Check
   the PayPal dashboard and webhook delivery for reconciliation; never mark
   it paid or reset its submission marker merely to retry. The sender item
   and batch ID are urban-payout-{local payout ID}. A verified item webhook
   can recover a missing batch ID after a lost provider response.
   Disputes/refunds/reversals block further customer charges and release.
   Do not retry failed transfers without reconciling the original transfer.

9. Sandbox acceptance: quote -> match -> 50% commitment -> start work ->
   helper completion -> customer confirmation -> 50% balance -> admin
   verification and tax review -> payout -> PayPal SUCCESS. Check provider
   fee amounts, full 60% helper amount, invalid signatures, duplicate
   captures, failed payouts and an interrupted payout response.
   Local automated tests fake PayPal; they do not establish live readiness.

10. Stripe endpoints are no longer routed. Historical Stripe records and
    schema remain for audit; do not relabel them PayPal or charge them
    again. Reconcile any in-flight Stripe sessions/transfers in Stripe
    before cutover. Existing unmatched opportunities need a fixed quote;
    existing matched Stripe jobs require a separate migration/reconciliation
    decision, since they do not have PayPal installments.

READABLE PAYMENT CENTER FOR AN EXISTING STATIC WEBSITE

The compiled customer-dashboard patch was withdrawn after a Microsoft
Defender detection. Do not deploy that archive or disable protection.
A separate readable implementation is in deployment/payment-center/.
It uses no third-party scripts, copied Next.js bundles, dynamic evaluation,
or external JavaScript dependencies. Automated tests verify functionality;
they do not certify an antivirus result.

1. Review index.html and payments.js. Leave antivirus enabled and scan the
   new files before deploying. If anything is flagged, stop and investigate.
2. Upload those two files to public_html/payments/ with file permissions 644.
   The source-only deployment/paypal-payment-center-source.zip contains
   the same two files beneath payments/ and can be extracted in public_html.
   No existing frontend assets need replacing.
3. In backend-api/app/Http/Controllers/PayPalPaymentController.php, use:
   'return_url' => $frontend.'/payments/?paypal_payment='.$paymentId,
   'cancel_url' => $frontend.'/payments/?paypal_cancelled=1',
   These values are already updated in this branch. Keep FRONTEND_URL set
   to https://urbanhelphub.com. Preserve all other runtime credentials.
4. Sign in normally on https://urbanhelphub.com, then visit
   https://urbanhelphub.com/payments/ using that same browser and hostname.
   Customers see installments, Helpers can save a payout email, and Admins
   can authorize and refresh payouts. All actions remain protected by the
   backend authentication and release rules. The existing dashboard's
   legacy Stripe button is not replaced; use the Payments page for testing.
5. Existing PayPal orders may retain their earlier return URL. If redirected
   to the old dashboard, return to /payments/ and use its payment button to
   reconcile the existing approved order; do not create another payment.
6. Run source tests using: node deployment/payment-center/payments.test.mjs
   PayPal credentials and real sandbox provider acceptance remain required.
